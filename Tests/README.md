# Scenario test suites

`Tests/` holds the in-game test runner (`Tests.lua`, the `/kaftest` command) and the scenario suites it shares with the headless runner `.claude/tools/headless/run-tests.lua`. `Tests/Files.xml` is the last entry in the `.toc`, so the suites ship with the addon and load after everything else, but the runner is only active in debug mode (Options > General > Debug). This README neither ships nor deploys: the release zip skips every `.md` file, and deploy copies only `.lua`, `.blp`, `.tga` and `.xml` files.

The rules that lean on these suites (a bug fix is built test first; every fixed bug leaves its scenario behind) are in `.claude/rules/tests.md`, which loads when a file here is read, and the kit's `krowi:process-issue` skill, with `docs/sdlc-playbook.md`, has the steps.

## Which suites to run

During development and in a pull request, run only the suites the change can affect, headlessly and in game; no full run when a change does not touch the feature. Before a release the gate (`.claude/release-gate.ps1`) wants a green in-game run of every suite below except `scheduler`, `sources` and `pictures`, on the newest Retail and Mists build, and, once per client version, a green full `/kotest` run of Krowi_Options' test addon. A run is green when it failed nothing and passed something, the rule `Run-GameTests.ps1` judges by too: a run that only skipped proves nothing (Krowi, 2026-11-08).

## Recorded and Target

Each scenario carries `Recorded`, the behaviour of the current code verified in game, and `Target`, the desired behaviour. A scenario passes when the code still behaves as recorded, and the scenarios whose target is still open are counted separately, so a behaviour change is a reviewable diff of the scenario file and the open defects stay visible without failing anything. Scenarios can carry `RecordedClassic`/`TargetClassic` where the clients differ.

## Running headlessly

`run-tests.lua` runs a suite in the vendored Lua 5.1 with WoW frames and the relevant FrameXML functions modelled from Blizzard's source. The model implements the same primitives for both clients (`-client Retail|Classic`, both by default) and provides only globals the game really has, so a call to a Blizzard local fails there too. The runner's header names the addon files each suite exercises.

```powershell
& "E:\World of Warcraft Addon Development\Krowi_ClaudeKit\tools\lua51\lua.exe" ".claude\tools\headless\run-tests.lua" "$PWD" escape           # every scenario line and a summary
& "E:\World of Warcraft Addon Development\Krowi_ClaudeKit\tools\lua51\lua.exe" ".claude\tools\headless\run-tests.lua" "$PWD" escape -check    # only the failures
```

`-check` prints a `<file>:<line>:` finding per failing scenario; it is what the `unit-tests` rule of `Check-Repo.ps1` runs.

One suite is headless only and has no file in `Tests/`: `runner` tests the in-game runner itself (docs/work/2026-11-08-test-run-history). It loads `Tests/Tests.lua` with stubbed game calls and drives `/kaftest` with fake suites: a run of 12 entries keeps all 12 runs in `History`, a single run after it trims `History` back to 10, a suite marked in `addon.Tests.FirstDraw` runs first, and a run from outside a `/kaftest run` that reports in between (a `/kaftest login` run) pushes none of its runs out. Its scenarios live in `run-tests.lua`.

A model of a secret value keeps the type the real value has: a secret name is a string that only the model's `canaccessvalue` rejects, a secret table is a table that errors when indexed and that only `canaccesstable` rejects. A stand-in of another type (a table for a name) is stopped by the code's type check, so the scenario passes with the secret-value guard removed. After writing such a scenario, remove the guard once and see it fail (2026-10-14-guide-npc-names).

## Running in game

- `/kaftest <suite>` runs a suite against the real frames (debug mode on, not in combat). `/kaftest login <suite>`, typed once, re-runs it after every `/reload` until `/kaftest login off`.
- `/kaftest <suite> <what>` runs part of a suite that takes it: `pictures` one picture or step, `options` one step or the steps whose name starts with it or the step with that number in the banner, each with the steps it builds on, or the set `smoke` (open and close), which Krowi_ClaudeKit's two-copy release gate runs where it needs no full run. Such a run is kept in `LastRun` and `History` with its `Argument`, but not in `Runs`, so the release gate (`.claude/release-gate.ps1`) only counts full runs.
- `/kaftest run <entry>[, <entry> ...]` runs several in order (an entry is a suite, or a suite and what to run of it: `options smoke`). Suites that need the achievement window's first draw of the session (`addon.Tests.FirstDraw`: `plugins` on Retail) run first, the others in the order typed. At the end a panel with each entry's counts and failed and skipped lines is screenshotted (`Read-GameScreenshot.ps1`), since the full results reach disk only at the next `/reload` or logout.
- `.claude/tools/Run-GameTests.ps1 <entries>` does a whole run with the kit's game-input tools, with nothing typed or clicked by anyone and nothing written into the game's files (Krowi, 2026-11-05; Krowi_ClaudeKit's `docs/work/2026-11-05-kit-test-runs`):
  - **The client:** it starts one, or reloads one that runs, then enters the world.
  - **The run:** it types `/kaftest run`, then waits for "done" from the kit's marker addon, then types `/reload`.
  - **Results:** it reads the results and BugGrabber's errors.
  - **Closing:** it closes a client it started.
  - **The mouse:** a step that needs the mouse (`pictures` `map-button`, `options` `settings-*`) asks the kit through the marker for its hover, key or click, so it no longer waits for a hand.
  - **Debug mode:** with the marker loaded and debug mode off, `/kaftest run` turns it on for the run and off again after the summary. Without the marker it asks for debug mode like `/kaftest`.
  - **Deploy:** deploying stays a separate step, before the run.
- Results go to chat and to `KrowiAF_DebugTable.Tests.LastRun`, which the game writes to disk on the next `/reload` or logout. `.claude/tools/Read-GameTests.ps1` prints that run with every line that differs from the headless run marked. The last 10 runs are kept in `KrowiAF_DebugTable.Tests.History`, so several runs in a row can be read after one `/reload`: the reader lists them, and `-Run <n>` shows the nth newest. A `/kaftest run` keeps every run it made, however many entries it has, so `Run-GameTests.ps1` reads all of them; the next run outside one trims `History` back to 10. Lines of steps only the game runs are marked `g` and not diffed, and a step's screenshot is paired with its file.
- A scenario is skipped there, with the reason stored, when state outside the scenario (a target, a foreign popup, an open menu, a UI panel) could have consumed a press.
- An addon cannot call `ToggleGameMenu` without `ADDON_ACTION_FORBIDDEN` from Blizzard's protected handlers, so the in-game press runs Blizzard's Escape chain as far as an addon may: the 12.1 handler registry on Retail, the legacy chain on Classic. `Tests/Escape.lua` documents both and their sources, and the headless model implements the same primitives.
- The in-game press never shows the game menu itself (its OnShow builds Blizzard's menu buttons in addon execution) and is not made at all when outside state could consume it.
- A suite can register a readiness check (`addon.Tests.Ready[<suite>]`); a login run waits for it, a manual run reports why it cannot run.

## The matrix run

`/kaftest matrix` (driven by `.claude/tools/Run-GameTests.ps1 -Matrix`, docs/work/2026-11-08-feature-split-poc) runs every suite but the probes (`scheduler`, `sources`, `pictures`) with every feature on, with every feature off and with each feature alone (with one feature, alone is all on), on the current profile's switches. A switch takes effect after a reload and `C_UI.Reload` is protected outside a key press or click (blocked from a timer on Retail 12.1.5 and Mists 5.5.4), so each step sets its switches and asks for a `/reload`, which the tool types; the plan carries over each reload in `KrowiAF_DebugTable.Tests.Matrix.Pending`. Its runs carry their step (`MatrixStep`) and stay out of `Runs`. After the last step the switches go back as they were and the record (`Matrix.Last`: per step how many suites ran, passed, failed and skipped) waits for the last `/reload`. `/kaftest matrix stop` drops a plan and puts the switches back. A suite whose scenarios need a feature that is off skips them with a reason; the `features` suite proves the absence. `memory` measures its idle minute in the all-on and all-off steps only; the single-feature steps are marked `SkipIdleMinute` and say so in its observations (docs/work/2026-11-12-matrix-run-length). The release gate wants a whole run, green, on the newest Retail and Mists build since `Features/` last changed.

## Remaking one help picture

On Retail with other addons off: `/console screenshotFormat png`, `/kaftest pictures <name>`, `/reload`, then `.claude/tools/Make-HelpPictures.ps1 -Only <Picture> -Preview <folder>`. Look at the preview over grey and over magenta, then run it again without `-Preview`. Only the last 5 runs are kept, so an older run cannot be remade from. The full world map hides the pink shot, so `MapButton` may need a second run. The scenes are fixed by the maintainer (2026-11-01), while a player's Show me keeps its own picks: achievement 42328 in the tooltips and the compact list, Mists of Pandaria in the category list, last month in the calendar, the Pop Out at full opacity, the summary's parchment alone (the step's `Alone` flag).

## Adding a suite

A new suite is a `Tests/<Suite>.lua` registered in `Tests/Files.xml`, a `suites.<name>` in `run-tests.lua` and a row in the table above. It checks something on every client it runs on: where what it covers does not exist, a read-only scenario checks that it does not, since a run that passes nothing fails `Run-GameTests.ps1` and the release gate.
