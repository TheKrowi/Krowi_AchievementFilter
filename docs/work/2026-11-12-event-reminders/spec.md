# Spec: Event reminders as a feature that switches off (106, step 4)
Intent: [intent.md](intent.md). Status: done

## Requirements

The feature
1. Event reminders registers as the feature `EventReminders` (title "Event reminders"), its switch the existing `EventReminders.Enabled`, default on. No saved key moves or changes meaning (`EventReminders.*`, the per-event `CalendarEvents`, `WidgetEvents`, `WorldEvents`; `KrowiAF_SavedData.EventObservations`, `ActiveEventPopUpsShown`, `ActiveEventChatMessagesShown`, `UpcomingCalendarEventPopUpsShown`, `UpcomingCalendarEventChatMessagesShown`), so no migration runs and a player who turned reminders off finds the feature off.
2. With the switch on, Event reminders behaves as on `main`, on Retail and Mists: the pop-ups and chat lines on login, on reload and when an event starts, the upcoming holidays, the side buttons on the achievement window or the world map and their menu, the scheduler, the fixed schedules and the watcher (Retail), the per-event toggles, both options sections, both help pages and their Show me.
3. With the switch off and the game reloaded: no pop-up, chat line or side button; no alert container, scheduler frame, `PLAYER_ENTERING_WORLD` timer, refresh ticker, watcher ticker or Blizzard_Calendar hook is made; no error is raised. The saved settings and per-event choices are kept and shown greyed; the watcher's learned starts and its log stay in the saved data.
4. Loading the feature's files makes nothing (no frame, hook, script, event, timer or slash command) and writes nothing into the saved data. The scheduler's frame (today made at file load, `Data/EventScheduler.lua:43, 212`) is made in `Start`.

What stays in the core
5. The event data stays the core's, whatever the switch: `KrowiAF.AddEventData`, the event objects (`addon.Data.Events`, `Objects/Event.lua`), the calendar cache and `KrowiAF_GetUtcOffsetSeconds` (`Data/EventData.lua:1-121`), the data files `DataAddons/*/EventData.lua` and `EventSchedules.lua`, the tables `KrowiAF.EventData`, `KrowiAF.EventSchedules` and the enums. The obtainable state, the Not obtainable tooltip and the special categories read them as today.
6. The Not obtainable tooltip formats its Date lines (`Data/TemporaryObtainable.lua:399, 455`) with its own date format (`Tooltip.Achievements.TemporarilyObtainable.DateTimeFormat`), as its other lines already do (`:291, 416-417`), so it reads no setting of the feature. Event reminders and the obtainable state are separate: the reminders are the side buttons, the pop-ups and the chat lines, and add nothing to a tooltip (Krowi, 2026-11-12); the obtainable state writes the Not obtainable lines of the achievement tooltip (`Gui/AchievementTooltip/NotObtainable.lua:13`) and of the row icon's tooltip (`Gui/WindowFrames/AchievementButton/AchievementButtonExtraIconFactory.lua:130, 149`), which until now read the reminders' date setting for these two lines only.
7. The Data Manager shows the watcher's log through a slot the feature fills; while the feature is off its debug view has no log tab (as on Mists today), and the Characters view works as before.

The boundary
8. The core opens nothing of Event reminders by name. Its starts run from the registry: `Start` at `ADDON_LOADED` (the alert container must exist before the login events, `Gui/EventReminder/AlertSystem.lua:193`), a new `AfterAchievementUI` phase once Blizzard_AchievementUI has loaded (the side buttons anchor on the achievement window, today `Gui/Gui.lua:107-109`), and the feature's own `PLAYER_ENTERING_WORLD` and `Blizzard_Calendar` listeners, registered in `Start` (today `Krowi_AchievementFilter.lua:87-89, 97-98, 106-108, 116-140`). The core keeps only the calendar cache's deferral reset on `PLAYER_ENTERING_WORLD` (`:115`).
9. The skins of ElvUI, GW2_UI and EllesmereUI are files of their own, `Plugins/<Plugin>/EventReminders.lua`, which the boundary rule gives to the feature; the plugins' own files name no Event reminders code. ElvUI and GW2_UI get the parts mechanism EllesmereUI has (`AddPart`, `Install`, `Apply`). A part hooks only a started feature, and hooks the side buttons' `Refresh` and the pop-ups' `SetUpAlert`, never `Load`, so a skin works though the feature now starts before the plugins load (`Krowi_AchievementFilter.lua:39, 41`) and the hooks no longer pile up on every `Load` (ElvUI `:795-803`, GW2_UI `:1159-1168`).
10. The public surface stays: `KrowiAF.AddEventData`, `KrowiAF.RegisterEventDataOptions`, `KrowiAF.InjectEventDataDynamicOptions`, `KrowiAF.EventData`, `KrowiAF.EventSchedules`, the enums, the frame names `KrowiAF_AchievementFrameSideButton<n>` and the templates `KrowiAF_EventReminderAlertFrame_*` and `KrowiAF_EventReminderSideButton_*`. `addon.Gui.EventReminderAlertSystem`, `EventReminderSideButtonSystem` and `EventReminderMenu` keep their names (the tests reach them, as Pop Out kept `addon.Gui.AchievementPopout`).

The options window
11. The two sections stay where they are (Around the game, after Criteria on units: Event reminders at Order 30, Reminder events at 40), with their headings, grids, families, All/None buttons and the Show/Hide buttons of the pop-up position, as today. The registry's switch replaces today's Enable row (`Options/EventReminders.lua:165-171`) on top of the Event reminders section. While the switch is off every row of both sections is greyed, and the sections' headings stay white as in the three features before.
11a. The Reminder events section, which has no switch of its own, opens with a line saying the Event reminders switch controls it, and a button after it that opens the Event reminders section (Pop Out's link button, 2026-11-09; Krowi, 2026-11-12). The line and its button never grey, so the way to the switch is never closed. They are rows of the feature's own group beside the switch (`Features.args.EventReminders.args`), outside its greyed Settings group; the line reuses `Feature Controls Desc`, the button's name follows Pop Out's "Go to {section}". Whether the window draws it as one row (a label with a button, as About's link rows) or a line and a button is settled at the look gate.
12. The per-event toggles are built after every data file loaded and before the options load, as `KrowiAF.InjectEventDataDynamicOptions` is today (`Krowi_AchievementFilter.lua:32`), now through the registry, so they exist (greyed) while the feature is off.
13. After a profile switch, copy or reset the reload prompt shows, as for every options-profile action (the grill, 2026-11-01); the feature's own live refresh on a profile action (`Options/EventReminders.lua:16-26, 795-802`) goes, since its owner moved (the PoC's decision, 2026-11-08, "keep until its owner moves").
14. Its settings and help texts go through the options review (what each does, name, description, help text; `REVIEW.md`, Texts), with the proposals put to Krowi at the look gate (`review-options.md`): names and descriptions that make sense in the section they are in, help texts that read the player's settings where they name one, and a plain-text sweep (Pop Out's look gate, 2026-11-11).

Help
15. Both help pages (`events`, `eventlist`) and their Show me stay; while the feature is off each opens with the off line and has no Show me. Today's "reminders were off at login" print (`ShowMe.lua:270-272`, `Help Events Off`) goes with it.

The headless `features` suite covers four features: files make nothing while loading, an off feature never starts and owns no slot entry, an on one does; Event reminders' own checks: no alert container and no listener frame while off, `AfterAchievementUI` runs exactly for a started feature, the Data Manager log entry exists exactly while it is started.

The headless suites `events`, `schedules`, `popups`, `memory`, `options`, `help`, `navigation` pass on the moved files, and a suite that loads a file by path fails when the file is missing instead of skipping it (`run-tests.lua:1588`, `:1646`), so a move can never leave a suite green on nothing.
19. `/kaftest matrix` through `Run-GameTests.ps1 -Matrix` is green on Retail and Mists with Event reminders added as a step: all on, all off, each feature alone. The `features` suite records the memory with Event reminders off and on.

## Design

### The folder
`Features/Files.xml` includes `EventReminders\Files.xml` after Pop Out's. The files keep their names (history and the work folders cite them), in subfolders as today:

| New file | From |
|---|---|
| `EventReminders.lua` | the registration (`Register`: `Start`, `AfterAchievementUI`) and the table `addon.EventReminders` |
| `Data/EventData.lua` | `Data/EventData.lua:123-337`, as `addon.EventReminders.EventData` |
| `Data/EventScheduler.lua`, `EventSchedules.lua`, `EventObserver.lua`, `CustomWidgetEventTimers.lua`, `CustomWorldEventTimers.lua` | the same files of `Data/`, as `addon.EventReminders.<same name>`; the scheduler's frame made in a `Start` function |
| `AlertSystem.lua`, `SideButtonSystem.lua`, `AlertFrame/`, `SideButton/`, `Menu/` | `Gui/EventReminder/`, names kept |
| `Options.lua` | `Options/EventReminders.lua` and `Options/Defaults.lua:164-270`, through `Features.AddOptions` |
| `EventOptions.lua` | `Api/EventDataApi.lua:20-164`: `KrowiAF.RegisterEventDataOptions` and `KrowiAF.InjectEventDataDynamicOptions`, defined here, called by the registry's options build |
| `Help.lua` | `Options/Window/Help/Help.lua:254-270`, `ShowMe.lua:266-284` |
| `DataManagerLog.lua` | the log tab's entry for the Data Manager slot |
| `Plugins/ElvUI/EventReminders.lua`, `Plugins/GW2_UI/EventReminders.lua`, `Plugins/EllesmereUI/EventReminders.lua` | the skin code of each plugin's file |

**Why `addon.EventReminders`:** `Features/` loads before `Data/` (the TOC), and `Data/Data.lua:4` makes `addon.Data`, so a feature cannot add to it while its files load. The feature's data modules hang on a table of its own; `addon.Gui` exists before `Features/`, so the GUI tables keep their names. The tests rename `addon.Data.EventScheduler` to `addon.EventReminders.EventScheduler` and so on, mechanically.

### What `Start` does
At `ADDON_LOADED`, after the options exist (`Krowi_AchievementFilter.lua:38-39`): the alert container (`AlertSystem:Load`, unchanged, before the login events), the scheduler's listener frame, one listener frame for `PLAYER_ENTERING_WORLD` (today's `:116-140` body, the calendar cache's deferral reset left in the core) and for `ADDON_LOADED` of Blizzard_Calendar (with the already-loaded case), the side buttons' `Load` for the world map anchor, and the Data Manager log entry. `AfterAchievementUI` loads the side buttons onto the achievement window (today `Gui/Gui.lua:107-109`). The refresh ticker and the watcher start where they do today, from the login timers.

### The registry and the slots (core)
- **`AfterAchievementUI`** in `Features.Register`: `Features.AchievementUILoaded()` runs it, in `xpcall`, for every started feature, from `LoadBlizzard_AchievementUI` (`Krowi_AchievementFilter.lua:56-72`), whose run-once latch covers both its callers (Blizzard's `ADDON_LOADED` and the already-loaded case at `PLAYER_LOGIN`). Achievement guides and Data Manager will need the same phase.
- **The options build moves to one step**: `AddOptions` records what a feature gives; `Features.BuildOptions()`, called where `KrowiAF.InjectEventDataDynamicOptions()` is today (after every file loaded, before `Options:Load`), merges the defaults, builds the rows, the `Into` rows and the sections, for every feature. A feature's `Late` function (Event reminders' per-event toggles) runs first in that step. For the three earlier features this only moves the build from file load to `ADDON_LOADED`; the options suite's fingerprint proves nothing else changed.
- **Several sections with the window's own entry kinds**: `AddOptions` takes `Sections`, a list of `{Id, Name, Card, CardIcon, NavGroup, Order, ChangedIn, Groups}`, where `Groups` are the map's own groups (`Options/Window/Map.lua:4-15`: `Path`, `Group`, `Families`, `Kind = "Grid"`, `AllNone`, `Buttons`, `Retail`, `Pairs`) with paths relative to the feature's settings group. The switch goes on top of the first section. `Section` (one plain group) stays for the features that need no more. The window's options already grey a row whose group is disabled, so the grids and families grey with the switch.
- **Several help pages**: `AddHelp` may be called once per page `Id`; each gets the off line and loses its Show me while the feature is off. `Features.List()` returns `HelpIds`.
- **`Slots.DataManagerTabs`**: `Add({Order, Name, GetText})`; the Data Manager makes its debug tabs (Characters plus one per entry) only when an entry exists, so with the feature off it shows the Characters view alone, as on Mists.

## Options considered
1. **The feature's own table `addon.EventReminders` for the moved data modules; a registry phase after the achievement window, one options build step, several sections and help pages, a Data Manager tab slot, and skin parts for every plugin (recommended).** The core keeps no trace of Event reminders; each new core part is small and the next features need it (Achievement guides and Data Manager the phase, Data Manager its tab slot, every feature with dynamic rows the build step).
2. **`addon.Data = addon.Data or {}` in `Data/Data.lua`**, so the moved modules keep `addon.Data.EventScheduler` and the tests keep their names. One line, but a feature then writes into the core's data namespace, and the boundary rule would count those names as the feature's inside a core table.
3. **The skins stay in the plugins' files, guarded by `IsStarted`.** Nothing to build, but the plugin files then name feature code, which the boundary rule fails, and the `Load` hooks miss the start that now comes before the plugins.
4. **The Date lines of the Not obtainable tooltip read a new core date format, or the feature's while it is on.** A core setting duplicates the tooltip's own; reading the feature's names the feature. The tooltip's own format is what its other lines already use (requirement 6).
5. **The follow mode's `AlertFrame:AddQueuedAlertFrameSubSystem` (`AlertSystem.lua:224`) rebuilt in this PR.** The workspace rules forbid that call since #188 (closing the What's New splash updates the objective tracker tainted), and it predates that rule. Rebuilding it changes how the pop-ups sit under ElvUI, GW2_UI, EllesmereUI and Dominos Roll, which needs those addons in game; a move should not change behaviour. Recommended: moved as it is, and a backlog item of its own.
6. **Two PRs** (the core parts first). Krowi chose one PR (2026-11-12).
